# FetchX Hetzner autoscaling implementation

Baseline: committed FetchX source 77169b9. Existing two local workers remain the base capacity. User approved eight additional VMs and EUR 40 per month before VAT, then explicitly requested three to four configurable VM choices with availability-based selection. All options share one ledger and budget.

## Admission contract

Add an opt-in `v2.browser_queue` for pool browser operations. Persist bounded metadata tickets in PostgreSQL before waiting, with project/key/hash uniqueness, per-project and global pending limits, FIFO within each project and round-robin between waiting projects. Do not store URLs, bodies, credentials or captures in queue metadata. Do not reserve request credits or source traffic before a slot is available. The normal operation transaction remains authoritative for quota, session, spending and global concurrency admission. Queue wait is bounded separately from browser execution (production 45 seconds). Client retries use the original idempotency key. Concurrent duplicate waiters receive a running response. Waiting tickets are cancelled on restart; they never execute autonomously. Existing operation recovery retains unknown reservations without redispatch.

Expose aggregate version-1 metrics only on the existing private callback Unix socket at GET /v1/pool-metrics:
`{version:1, generated_at:<ISO>, queue:{pending,active,oldest_wait_ms,recent_timeouts}, workers:[{id,state,ready,busy}], max_concurrent_requests:<integer>}`.
Metrics contain no project identities, request keys or destinations. Counters represent waiting/claimed queue tickets and recent pre-dispatch timeouts (last 5 minutes). Runtime qualification remains pinned. A stale or unavailable metrics snapshot prevents growth and does not permit deleting busy/unknown work prematurely.

## Controller contract

A separate root-only Python standard-library systemd daemon owns a durable SQLite infrastructure ledger, cloud API token, registry edits and tunnel administration. The gateway receives no cloud credential. Controller configuration includes explicit enabled switch, unique deployment label, max additional VMs, monthly EUR micro-unit budget, approved hourly ceilings for server and IPv4, explicit HEL1 machine options (CX23, CX33, CPX22, CCX13) on Ubuntu 24.04, boot timeout, scale-up delay/cooldown, idle drain delay, max VM lifetime and cleanup reserve. Missing/invalid config, price increases, lost/corrupt state, duplicate ownership, stale demand or uncertain API results fail closed for creation.

Reserve each VM's entire maximum lifetime plus a cleanup allowance, using rounded hourly server and IPv4 rates, before POST /servers. Charge every possibly billable hour conservatively until deletion is confirmed. Account for UTC month boundaries, never reset unresolved liabilities, and retain uncertain-create reservations. Label each request with a durable unique identity, reconcile by that identity and never blindly retry POST after a timeout. Only explicitly owned resources can be drained/deleted. Server deletion must confirm IPv4 deletion (auto_delete plus explicit reconciliation). Only explicitly configured, live-eligible server sizes may be selected. No snapshots, backups, volumes or paid proxies are created.

Scale up one worker after sustained queue pressure when all current slots are occupied, with cooldown and both resource/budget caps. Include booting workers in the desired count. Scale down idle extras by atomically marking registry entries draining, observing completion, then deleting cloud resources. A hard lifetime and worker lease prevent indefinite use if the controller fails; API unavailability can still delay actual resource deletion and billing. This is an application-enforced infrastructure budget, not a provider-side invoice lock.

## WorkerDriver interface (shared by controller and provisioning implementation)

`WorkerDriver(config)` lives in `ops/autoscaler/worker_driver.py`.
- `prepare(record)` returns a dict with `user_data` (cloud-config string); must persist generated host/tunnel keys under state_dir before returning. `record` has `id` (safe lowercase alphanumeric/hyphen <=32), `created_at` (epoch seconds), `lease_expires_at` (epoch seconds). Idempotent across restart. Cloud-config authorizes the controller's separate admin public key and optional user-authorized PortTrack public key; never copies the PortTrack private key. Host keys are pinned before connecting.
- `bootstrap(record, server)` is synchronous, bounded by config boot_timeout_seconds. Idempotently installs the pinned assets, starts a hardened single-slot network-none container, establishes a private SSH Unix-socket tunnel with a separate per-worker key, and validates browser runtime/callback readiness. Runs in a controller background future so reconciliation and cost controls continue. Returns `{socket_path:<gateway-visible /run/fx/registry/...sock>}` only when ready. `server` is the API server object with IPv4. Does not mutate the gateway registry or create/delete cloud resources.
- `disconnect(record)` stops only the owned tunnel and cleans its socket. Safe to repeat; does not delete a VM.

Required config driver keys: `state_dir`, `registry_path` (host path), `gateway_registry_dir` (container path), `callback_socket` (host path), `ssh_admin_key`, `porttrack_public_key` (optional text), `asset_manifest`, `boot_timeout_seconds`, `worker_lease_seconds`. Asset manifest is a private operator-produced JSON with image archive/hash/ref and ordered RootFS layers, browser archive/hash, runtime pin, browser executable and seccomp file/hash. Driver and controller may add validated keys but must agree before integration.

## Verification and rollout

Use fake cloud responses and synthetic source fixtures. Test fair queue bounds/timeouts/duplicate keys/restart/no credit reservation while waiting; simultaneous claims; browser unknown no redispatch; cloud price/budget/instance caps; month rollover; create timeout reconciliation; stale metrics; restart; drain while busy; owned-only cleanup; IPv4 deletion. Tests requiring PostgreSQL run serially against gateway_test_* only. Include real browser and TLS recipe acceptance. Stage the production candidate without customer data, then perform bounded real cloud growth, queueing, source counts, drain and controller restart tests after budget authorization. Deploy with a current encrypted paired backup, migration/rollback review and exact image/browser pin checks. Record actual limits, costs and acceptance evidence. Never publish private operational artifacts.
