# FetchX contributor guidance

This is the platform; fetching lives in the private engine repository (karthikbala/fetchx-engine). Keep these intact: project isolation, success-only billing (reserve at admission, charge only the winning step from the engine's `usage`, release otherwise, settle each job exactly once), sealed storage of webhook URLs and secrets, idempotency (the same key and body never runs or charges twice), never resending a job whose outcome is uncertain, and public-address checks after DNS for customer webhooks. Never put site-specific behaviour in either repository.

`docs/openapi.json` is the public API contract. Change it first, run `npm run api:generate`, then change the code; `test/api-contract.test.mjs` checks routes, scopes and real responses against it. `docs/engine-api.json` is a pinned copy of the engine's contract: change it in the engine first, copy it here, and keep `test/engine-contract.test.mjs` and `test/fake-engine.mjs` passing.

Run tests serially against an explicitly disposable `gateway_test_*` PostgreSQL database, with the fake engine and fake providers: no credentials, paid calls, real engines or real sites in tests. Run the website's checks when changing the console API. Never publish customer data, production diagnostics or secrets. GitHub Actions is paid: don't rely on it or trigger it. Run the suite yourself before pushing; the release runs it again inside the built image on the server (tree read-only, throwaway PostgreSQL) before any deploy.
